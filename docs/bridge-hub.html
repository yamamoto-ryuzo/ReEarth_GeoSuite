📚 AIチャット → ブリッジハブ連携

🏠 GeoSuite トップ ドキュメント一覧 GitHub で編集

AI チャットのプロバイダのうち GitHub Copilot と External agent（外部エージェント） は、API キーで直接叩く系統とは別経路で、ローカル常駐の CANVAS ブリッジハブ（bridge-hub.exe・127.0.0.1:8511） へ HTTP POST する「ブリッジ系」です。v21.3.0 追加。

本ページは「ブラウザ → エージェント」（チャットから AI を使う）方向の説明です。逆方向「エージェント → ブラウザ」（外部ハーネスから地図ツールを遠隔実行する外部ブリッジ / bridge: 行 / __geoBridge）は external-bridge.html を参照してください。

bridge-hub は オプションの拡張コンポーネントです。geo_suite の地図表示・レイヤー管理・Gemini 等の API 直接プロバイダはハブなしで動作します。必要になるのは GitHub Copilot (bridge hub) プロバイダと、後述の /vector 自動外部化を使う場合だけです（/vector 外部化はハブ未到達時に従来の iframe デコードへフォールバックします）。KASUGAI Canvas アプリをインストール済みの環境ではセットアップが自動導入するため個別インストールは不要です。

導入方法（Ext ボタン／管理パネル Ext タブ・v22.3.0〜）

ハブが未検出の環境ではプラグイン内に導入導線が表示されます。導入手順は ① ZIP をダウンロード → ② 展開 → ③ bridge-hub.exe を実行 の3ステップで、exe は1回実行するだけで %LOCALAPPDATA%\kasugai\bridge-hub\ へ自己インストールされ、ログイン時の自動起動も登録されます。

  • レイヤーパネルの Ext ボタン（レイヤー見出し「Note」の右）: パネル iframe は起動ごとに、エンドポイント解決結果（vectorHub: > aiHub: > 127.0.0.1:8511）へ GET /health を1回プローブし、hub:true が返らない場合ボタンをアンバー強調します（未導入の訴求）。押下で直下のプロモ行を開閉します
  • 「Download bridge-hub.zip」ボタン: <a download> で kasugai-canvas-web CDN（stable チャンネル）から ZIP を取得します。環境によって裸 .exe の直ダウンロードがブロックされるため v22.3.1 で ZIP 同梱形式へ切替済みです。押下後は起動待ち表示へ切替り、/health を2秒間隔・最長3分ポーリングし、検出次第「connected」表示 → 4秒後に行を自動で閉じます（期限超過時はリトライ案内を表示）
  • プロモ行右端の − ボタン: セッション中はプロモ行とボタン/サブタブの強調を非表示にします（dismiss 状態は _hubInstallCfg.dismissed として注入されるため iframe 再生成を跨いでも消えたまま）
  • 管理パネル（⚙️）の Ext サブタブ（v22.3.1〜）: bridge-hub: ON/OFF の状態行＋疎通確認ボタンと、レイヤーパネルと同一の導入ブロックを常設しています。「AI Bridge (CANVAS)」のエンドポイント入力（aiHub: 行と双方向同期）もこのペインに移動済みです。ハブ未検出時は Ext サブタブもアンバー強調（dismiss 後は抑制）、検出済みなら導入ブロックは自動で非表示になります
  • vectorHub: off 指定時: Ext ボタンと Ext ペイン内の bridge-hub ブロックは非表示になります（AI Bridge 設定は残ります）

細かいペイロード（tools/camera/toolResults の往復）と detectHub() の検出手順は下のシーケンス図・後述の節を参照。直接 fetch 系（Gemini / OpenAI互換など）も同様のツール往復を行い、違いは応答をハブ経由で受け取るか API から直接受け取るかだけです。

ハブ側は各プロバイダの CLI を子プロセスとして遅延起動し、その公開インターフェース経由で応答を取ります（Copilot なら copilot --server --stdio へ github-copilot-sdk の JSON-RPC）。認証・クォータは CLI 側の本人ログインに委ねられ、ブラウザは API キーを持ちません（Copilot/agent プロバイダはキー欄が不要＝no key (bridge) 表示）。

通信シーケンス（サンドボックス → AI API 直接）

まず通常の API 直接接続です。Gemini・OpenAI互換・Anthropic・Azure・Sakura の各プロバイダはハブを介さず、iframe から設定エンドポイントへ API キーを同梱して直接 fetch します。ツール呼出しは各 API ネイティブの形式（functionCall / tool_calls / tool_use）で返り、結果もプロバイダ固有の履歴フォーマットで次リクエストへ積む往復ループです。

なお fetch は opaque origin の UI iframe 側でのみ実行でき、QuickJS 拡張コンテキストはメッセージ中継（postToParent / aiToolCall ↔ aiToolResult / aiToolRequest）しか担いません。この後の2図に出る「拡張ctx がツール実行」はこの中継を指します。

通信シーケンス（サンドボックス → ブリッジ → AI）

GitHub Copilot / External agent のブリッジ系は、同じツール往復をローカル常駐の bridge-hub（127.0.0.1:8511） 経由で行います。直接接続との違いは (1) detectHub() による接続先検出がある代わりに API キーが不要、(2) ハブ側ローカル状態ツール用に camera/layers/basemaps を毎往復取り直して送信する、(3) ツール結果が履歴フォーマットではなく POST ボディの toolResults フィールドに乗る、の3点です。

エンドポイント解決（detectHub）

ハブの接続先は次の優先順で決まります:

  1. AI チャット設定画面の Endpoint 欄（明示指定が最優先。末尾の /agent は剥がしてベース URL 化）
  2. インスペクタの aiHub: <url> 行 — 管理パネルの「AI Bridge (CANVAS)」ブロックの入力欄と双方向同期し、aiConfig メッセージで AI チャットへ伝搬（Endpoint 欄が空のときのプリフィル）
  3. 自動プローブ — 上記が無ければ http://127.0.0.1:8511/health を 1 回だけ GET し、応答すれば http://127.0.0.1:8511 を採用（bridge-hub.exe が常駐していれば自動接続）

管理パネル「AI Bridge (CANVAS)」の Test ボタンは /health + /models?provider=copilot を叩いて疎通・モデル数・プロバイダ一覧を表示します。

モデル一覧の取得

プロバイダ選択時に GET {base}/models?provider=copilot を叩き、返ってきた一覧をモデル欄の datalist に反映します。ハブ未到達時は hub: unreachable — install/start bridge-hub.exe (port 8511) と表示されます。

bridge ツール canvasApi

外部ブリッジ（external-bridge.html の経路）越しにハブの REST を叩けるツールとして canvasApi があります。{path, method, body, endpoint?} で <base>+path へ fetch し、{ok,status,json|text} を返します。navigation-toolbar の永続 iframe で実行されるため、外部エージェントが /setup や /mcp 等のハブ API をブリッジ越しに利用できます（v21.3.0〜）。

ブリッジハブ（bridge-hub.exe）側の概要

  • Rust 製の単一 exe（Node.js 不要）で 127.0.0.1:8511 のみバインド。%LOCALAPPDATA%\kasugai\bridge-hub\ へ自己インストール＋ログイン時自動起動
  • プロバイダは copilot / devin / antigravity の 3 系統。実際に使われた時点で対応 CLI を子プロセス起動（未使用時はゼロコスト）。CLI 未導入なら POST /setup で公式手順の自動インストールも可能
  • 認証は CLI 側（Copilot なら copilot CLI の対話ログイン or COPILOT_GITHUB_TOKEN/GH_TOKEN/GITHUB_TOKEN）。クォータは利用者本人のものを消費
  • API: GET /health・GET /models?provider=・POST /agent・GET|POST /setup・POST|DELETE /mcp[/<project>]・GET /（状態ページ）・/vector/*（status/sources/geojson/query + probe.geojson は LNA アンロック用プローブ、v6.19.0〜）
  • GeoSuite の AI チャットが送れるのは provider:"copilot"（専用選択肢）と汎用 provider:"agent"。devin/antigravity 宛の送信は現状 GeoSuite 側 UI に無い

ハブの詳細仕様（導入・自動セットアップ・プロバイダ別前提・環境変数）は KASUGAI Canvas 側のドキュメントが正本です: ブリッジハブ（bridge-hub.exe）— KASUGAI Canvas ドキュメント

/vector — ベクトルソースの自動外部 GeoJSON 化（v22.2.0〜）

ハブの /vector サービス（ネイティブ DuckDB CLI をバックエンドに parquet/gpkg/fgb/geojson/csv/shp を永続 .duckdb へ取り込み GeoJSON 配信）が稼働している環境では、拡張経路ベクトル構文のうち http(s) URL を持つ fgb:・parquet:・gpkg:・duckdb: のソースを自動でハブ登録し、geojson: http://<hub>/vector/geojson/<name> の素の URL レイヤとして追加します。

これにより DuckDB-Wasm の ~15s 初期化・opaque origin のキャッシュ不可・拡張コンテキスト 4MB 制約を全て回避できます（結果は ctx を横断せずホストが直接 fetch）。同一ソースは gs_<hash> の決定的名で登録されるため、再読込・他クライアントで取込み済みテーブルが共有されます。

インスペクタ側オプションハブ側へのマップ
where=・limit=・table=（gpkg は layer=）・lon=/lat=・geom=（geom_col）POST /vector/sources の登録ボディ
format=（duckdb）kind（parquet/csv/json→geojson/gpkg/fgb。未指定は拡張子からハブが推定）
columns=配信 URL の ?columns=a,b（登録ではなく配信時の列選択）
style=/qml=・| off・分類（terrain 等）追加される geojson レイヤへそのまま引継ぎ
  • 対象外（従来どおり iframe 内デコード）: kasczip メンバ・eager dataB64・.duckdb ファイル・geojson: 行自体（元からホスト fetch）。sql: 行と AI ツール addDuckDbLayer も外部化対象で、sql: クエリは kind:"sql" の VIEW（materialize:false）として登録されます（duckdb: … format=read は SELECT * FROM ST_Read(url) の kind:sql ビューに変換）
  • フォールバック: ハブ未到達（/vector/status プローブ 3s タイムアウト）・登録失敗時は既存の iframe デコード経路をそのまま実行するため、ハブの有無で挙動が壊れません
  • 制御行: vectorHub: off で無効化、vectorHub: http://host:port で接続先指定。省略時は aiHub: の値、それも無ければ 127.0.0.1:8511 を自動検出（AI チャットと同じエンドポイント解決）
  • bbox=auto の扱い: 外部化されたレイヤの geojson URL にはビューポート範囲が ?bbox= パラメータとして付き、カメラ移動時は data.url の差替えのみでホストが再 fetch します（再登録・ctx 横断なし）。sql: 側の :bbox はビュー内で世界エンベロープへ焼き込み、実フィルタは URL 側に移譲されます
  • デコード失敗時のトゥームストーン・⏳ ロード中行・armPendingTtl（300s）は既存経路と同じ枠組みで処理されます

通信面の補足: ハブ呼出しはパネル iframe の hubExternalize ハンドラで GET /vector/status → GET /vector/sources → 必要時のみ POST /vector/sources（text/plain・プリフライト不要のシンプルリクエスト）を1往復で行い、結果は hubResult で拡張ctxへ返ります。登録ボディの name は kind/src/where/limit/lon/lat/geom_col の FNV-1a ハッシュから決定的に生成します。

実機検証で判明した運用上の注意（v22.2.0）

  • 適用ストーム中の iframe 再生成 — inspector 一括適用ではレイヤ着地ごとの safeShowUI がパネル iframe を再生成し、in-flight の POST /vector/sources が abort されて無言で wasm フォールバックに落ちることがあります（既登録ソースは probe のみで潜り抜ける。静穏時・単行適用では正常）。対策候補: hubExternalize の永続 basemap iframe 経由化、または ext-path drain 中の safeShowUI coalesce
  • フォールバック側はソースの CORS が前提 — wasm/iframe デコード経路は opaque origin の iframe がソース URL を直接 fetch するため、Access-Control-Allow-Origin を返さないサーバ上のソースは全て Failed to fetch で失敗します。この場合外部化が唯一の動作経路になります（検証用の python -m http.server 等は ACAO 無しでフォールバック不可）
  • format=read の適用範囲 — SELECT * FROM ST_Read('url') の kind:sql VIEW は GDAL 可読フォーマット専用です。.parquet では 502→フォールバック、.gpkg URL では拡張子判定が先に効き kind:gpkg 登録になります
  • vectorHub: http://host:port の効力範囲 — その適用パス以降の全ソース（qgis: インクルード分を含む）の接続先になります
  • 再適用の二重追加は抑止済み — ext-path アイテムは isLayerLoading(url) の in-flight チェック＋着地後の title 重複判定で、適用が短時間に重なっても同一ソースを重複追加しません（v22.2.0 で全 type に適用。sql: 行がディスパッチされず外部化に到達しない問題も同版で修正）
  • ハブ側の既知課題（kasugai_canvas） — duckdb_lock の直列化により取込みハング時に全 /vector リクエストが無音待機になります（#46。クライアント側は hubResult が来ず 300s TTL まで無応答）。また sources.json↔実テーブル不整合で manifest 比較のみの stale 判定をすり抜け、死んだ geojson URL を指すレイヤが追加され得ます（#42）

Chrome Local Network Access (LNA) と自動アンロック（v22.4.0〜）

  • 症状: Chrome 142+ では公開 HTTPS ページ上のプラグイン iframe（opaque origin）から 127.0.0.1:8511 への fetch がサイレントに拒否されます（コンソールには Permission was denied for this request to access the loopback address space）。権限状態は prompt のまま失敗し、iframe 起点では許可プロンプト自体を出せません。ハブ・ZIP・URL・CORS が全て正常でも接続できません
  • 権限はトップレベルサイト紐づき: いったん許可すれば iframe のプローブも全て解放されます。そして トップレベル（ホスト）コンテキストの loopback fetch だけは標準の許可プロンプトを出せます
  • 自動アンロック（v22.4.0〜）: ハブ未検出のままユーザーが Ext を開いた時・ダウンロード後の起動待ち時に、{hub}/vector/probe.geojson を指す一時 geojson レイヤを追加します。data.url はホスト側が fetch するため Chrome の「ローカルネットワークへのアクセス」プロンプトが自動表示され、1回「許可」するだけで以後の全接続が解放されます。検出次第プローブレイヤは自動除去（最長120秒ポーリング）。bridge-hub v6.19.0 で専用エンドポイントを追加済みですが、旧ハブ（404 応答）でもプロンプトは発火します
  • 代替経路: Firefox（LNA 未施行）・Chrome 起動フラグ --disable-features=LocalNetworkAccessChecks・企業ポリシー・または aiHub:/vectorHub: へ https トンネル URL（cloudflared・Tailscale serve 等）を指定すれば宛先が公開 https になり LNA の対象外です。プロンプトで「拒否」を選んだ場合はサイト設定から手動で許可し直してください

設計上の制約・注意

  • 通信は全て iframe 側で行う — QuickJS 拡張コンテキストには fetch が無いため、callAgent・detectHub・/models 取得はすべて ai-chat UI iframe 内ブラウザ JS です
  • opaque origin からの localhost POST — iframe はサンドボックス（opaque origin）なので application/json POST は本来 PNA プリフライトが必要ですが、ハブ側が Access-Control-Allow-Private-Network: true 付きの permissive CORS で応答するためそのまま通ります（外部ブリッジ側で text/plain 化しているのとは対照的に、ハブがサーバ側で対策済み）。ただし Chrome 142+ の LNA は CORS より先に効くため、上記の自動アンロック（サイトへの loopback 権限付与）が前提になります
  • ローカル・本人利用限定 — ハブの各プロバイダは公式連携ではなく公開インターフェースを使うサードパーティ製クライアントです。127.0.0.1 バインド・本人アカウントの CLI で使ってください
  • apiKey は送らない — Copilot/agent プロバイダではキー欄が無効（no key (bridge)）。外部エージェントへキーを同梱する経路は GeoSuite 側にはありません
  • ハブがいなければ失敗するだけ — 8511 プローブは 1 回だけ。ハブ未起動でも地図・他プロバイダには影響しません
