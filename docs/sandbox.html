※ 「外部ブリッジ」はサンドボックス外のローカル常駐プロセスの総称で、役割が2系統あります — bridge_server.js :8977（外部からのツール呼出し専用）と geosuite-hub :8514（AI エージェント中継＋/vector 外部化）。巨大ベクターソースはサンドボックス内で永続化・デコードできず（opaque origin のため DuckDB-Wasm アセットが毎セッション再ダウンロード＋~15s 初期化、元データも毎回再取得・結果は 4MB 上限）、これが動作を遅くしていたため、geosuite-hub の /vector サービスへ外部化しています — ハブ側のネイティブ DuckDB がローカル .duckdb へ永続取込みし、geojson: URL レイヤーとしてホストへ直接配信します（詳細・次節の容量目安を参照）。

📏 ベクトルデータの容量目安（必読）

サンドボックスを横断しない経路は容量の制約がありません。 次の2経路はデータ本体が Re:Earth のプラグインサンドボックス（QuickJS wasm メモリ）を一切通らず、Visualizer ホスト側が直接 fetch・パースするため自由度が高い経路です:

  • 正規経路（URL 指定レイヤー）: geojson: / xyz: / 3dtiles: / base: など。data.url の URL 文字列だけが ctx を通り、本体はホストが直接取得します。通常のレイヤー追加はまずこの経路です。
  • geosuite-hub /vector 外部化（v22.2.0〜）: ローカルの geosuite-hub（127.0.0.1:8514）が稼働していれば、fgb: / parquet: / gpkg: / duckdb: / sql: の http(s) ソースはハブの永続 DuckDB に取り込まれ、geojson: URL レイヤーとして正規経路に合流します。wasm 初期化・4MB 上限・再取得コストを全て回避できます（詳細）。

制約が掛かるのはフォールバックのプラグイン拡張経路だけ — ハブ未到達・vectorHub: off・非 http(s) ソース（ファイル取込・kasczip メンバ）の場合に、geo_suite がブラウザ内 iframe でデコードして data.value として注入する経路です。Re:Earth のプラグイン拡張は QuickJS (WebAssembly) コンテキストで実行され、全拡張が 1 つの wasm 線形メモリを共有します。iframe ↔ 拡張 ↔ ホスト間のメッセージは全て JSON.stringify → 共有メモリへの文字列コピー → JSON.parse で往復するため、巨大なペイロードは共有ヒープを圧迫し、OOM で拡張コンテキストごと全滅します。つまりCesium やブラウザの性能ではなく、Re:Earth サンドボックス固有の上限です。

このため拡張経路に「横断ペイロード 1回あたり 4MB（JSON サイズ）」のハード上限を設けています。超過したレイヤは追加されずレイヤ一覧に ⚠ グレーアウト行（理由付き）として残ります。

注入方式ごとの推奨容量

方式上限推奨の目安
geojson: <URL>（ホスト側が直接 fetch）4MB 制約なしVisualizer が URL を直接取得するためサンドボックスを通らない。大きな GeoJSON はまずこの方式（検索インデックスは 8MB 上限の対象）
fgb: / parquet: / gpkg: / duckdb: / sql: の http(s) ソース → geosuite-hub 外部化4MB 制約なしハブ稼働時は geojson: URL レイヤー化して正規経路に合流（vectorHub: off で無効化・ハブ未到達時は下行のデコード経路へフォールバック）
ファイル取込 / geojson: の kasczip メンバ（デコード注入）4MBiframe でデコード→ctx 注入のため制限あり。超えたら qgis: 外部ホスト参照へ
duckdb: / sql: / gpkg:（クエリ結果）4MB / クエリbbox=auto（既定・表示範囲連動）＋ where=/limit=/columns=/table= で絞れば 元データは数百MBでも可
flatgeobuf: / parquet:（全件デコード）4MB全件読みのため小〜中規模向き。大規模は duckdb: に置き換え推奨
qgis: ZIP ドロップ取込（eager メンバ）8MB 合計ZIP は URL 参照（ホスト配置）推奨 — メンバは遅延 fetch され本体容量を問わない
ベクター検索インデックス1ソース 4MB / 合計 8MB超過レイヤは検索対象外になるだけで表示は有効

運用の推奨

  • まず「URL 経由」を選ぶ: geojson:/3dtiles:/xyz: 等の URL 指定レイヤーは Visualizer ホスト側が直接 fetch するため、サンドボックス上限を受けません。ファイルはドロップではなく CMS 等に置いて URL で参照するのが基本です。
  • geosuite-hub があれば制約自体を回避できます: ローカルで geosuite-hub（:8514）が稼働していれば、http(s) 上の fgb:/parquet:/gpkg:/duckdb:/sql: ソースはハブの永続 DuckDB に取り込まれ geojson: URL レイヤーになるため、iframe デコードも 4MB 上限も通りません（v22.2.0〜・詳細）。
  • 総量の目安: ハード制約は「ctx を横断する結果 ≤4MB/回」のみ。レイヤ数自体に上限はありませんが、属性検索・一覧を快適に使うなら検索対象のベクトルデータ合計で数10MB 程度を目安にしてください。
  • 大規模データは絞り込み前提で: 巨大ファイルは duckdb:（GeoParquet/CSV/JSON）か gpkg: で、bbox=auto の部分読み込み＋属性フィルタを使い、「クエリ結果だけが 4MB 以下」になるよう設計してください。元データのサイズは問いません。
  • 配布は URL 参照で: プロジェクト一式は CMS 等に置いた qgis: <.kasc または .zip の URL> を推奨。ZIP の中身はブラウザが直接 fetch するため容量制限を受けません（ただし ZIP 内 geojson 等は kasczip デコード注入のため 4MB/件）。
  • 失敗は可視化されます: 上限超過レイヤは消えず、レイヤ一覧に理由付きのグレーアウト行として残ります（× で削除、条件を直して再読み込みで自動置換）。
